# Modular distribution — Phase 1: audit and target design

Status: **proposal, nothing moved yet.** Read-only audit of `D:\smart-school-management` at commit `f1539ee` (branch `feat/convex-backend-foundation`). Per-file evidence is in [appendix-a-file-ownership.md](appendix-a-file-ownership.md), generated by a static scan of every `import`, every `api.*` reference and every `ctx.db` table access (308 files: 236 under `src/`, 72 under `convex/`).

Goal restated: a school that buys **Students + Attendance** receives the source of Core, Students and Attendance only — no Academics, Fees or Examinations source, routes, functions, schema or packages — and every combination (including all five) builds, runs and integrates.

---

## 1. Executive summary

1. **Runtime entitlements already exist and are solid, but they are not source isolation.** `convex/core/modules.ts` + `schoolModules` gate every module function on the server and drive navigation/route guards. That stays (it is what our own multi-school deployment needs), but every module's code is still present, imported and deployed.
2. **The current module catalogue does not match the five requested modules.** Today: `students`, `academics` (= examinations + timetable + homework), `attendance` (= student attendance + staff attendance + leave), `finance`, `administration` (= notices, events, reports). Academic *structure* (years, classes, sections, subjects, teacher assignments) is deliberately **core**. Homework, notices/events, reports and staff attendance/leave have no home among the five requested modules.
3. **The biggest structural blocker is placement.** Students' own tables point at the academic structure: `enrollments` → `academicYears`, `classes`, `sections`. If Academics *owns* classes and sections (as the brief says), Students cannot exist without Academics and the flagship "Students + Attendance" product is impossible. This needs a decision (§5, D1).
4. **Coupling is mostly reads, not writes.** Every table is written only by its owner, except `convex/academics.ts` (which mixes structure, students and assignments) and `convex/seed.ts`. The cross-module coupling is reads: the student profile/records (`model/studentRecords.ts`) read fees, results, homework and timetable; the TC dues gate (`model/lifecycle.ts`) reads fees, results and attendance; reports, dashboards and the student portal read everything.
5. **There are two backends.** Besides Convex, the browser demo mode (`src/lib/services/*` + `src/lib/mock-data/seed.ts`, 742 lines) is a full second implementation of every module behind one `Services` registry, with cross-module service calls (e.g. students → fees). It cannot be split without either per-module demo services or dropping demo mode from customer distributions (§5, D4).
6. **Source exclusion is achievable in this repository** with a monorepo-style layout inside the same Next.js app and Convex project, a generated module registry, composed schema, and an export script that copies an allow-list, regenerates `convex/_generated`, and verifies with type-check, build, tests and a forbidden-path scan. No separate Convex deployment per module is needed. Each distribution has its own deployment.
7. **Git history is the real leak.** Exporting from this repo must ship a fresh tree without `.git` (or a fresh per-customer repository). Otherwise every past commit carries every module.

### 2.1 Three concepts that must stay separate

### 2.5 Frontend facts that matter

- **Routes** are thin `src/app/**/page.tsx` wrappers. Most choose between a demo and a live feature component (`PortalPage demo={…} live={…}`). Next.js discovers every `page.tsx` on disk, so an excluded module's routes must be absent from the tree, not just hidden.
- **Navigation and route guards** (`src/lib/permissions/navigation.ts`, `routes.ts`) are one hard-coded list for all modules, tagged `module: "students" | …`. They already fail closed on modules.
- **Shared domain types**: `src/types/domain.ts` (472 lines) mixes every module's types and is imported by 20+ Core files.
- **Shared UI kit** (`src/components/ui/*`) is genuinely shared and module-agnostic. One exception: `chart-card.tsx`/recharts is used only by Attendance, Fees, Exams, Students and the adapters.
- **Packages**: Core needs Next/React/Convex/auth/radix/framer/zod/react-hook-form/read-excel-file. `recharts` is used by modules and adapters only. `qrcode-generator` is used by Students only (TC verification).

### 2.6 Convex facts that matter

- Convex deploys **every** `.ts` file under `convex/` (except `_generated`) as functions. A function's API path is its file path: `convex/students/lifecycle.ts` → `api.students.lifecycle.*`. Excluding a module's functions therefore means **its files are not in `convex/`** when `convex dev/deploy` runs.
- `convex/_generated/api.d.ts` is produced by `npx convex codegen` from the files actually present. It is **not** something to hand-maintain or ship. Each distribution regenerates it from its own included files, so it never mentions excluded modules (§7.3).
- The schema is one `defineSchema` in `convex/schema.ts`. Tables can be declared in separate modules and composed with object spread, because `defineSchema` takes a plain object of `defineTable(...)` values.
- One cron (`crons.ts`) references `internal.feeReminders.runDaily` (Fees). Crons must be contributed by modules, not hard-coded in Core.
- Existing guards: `tests/convex/permissions.test.ts` (no raw public functions) and `tests/convex/module-entitlements.test.ts` (every public function classified to a module). These are a good base for the new ownership tests.

## 4. Target architecture

### 4.1 Layout — adapted to Next.js and Convex, not a rewrite

A full multi-package workspace (`apps/` + `packages/` + separate `node_modules` graphs) would force a second Next.js app and a Convex components conversion. That is far more change than isolation needs. Both tools tolerate **nested folders inside their own roots**, so the module boundary is a folder per module in each root, plus generated registries:

```
src/
  core/                     # was components/, lib/, features/{auth,accounts(staff),settings,profile,audit,notifications,shared}
  contracts/                # public, dependency-free: branded ids, module manifest types, event types, provider interfaces
  modules/
    students/               # index.ts (public entry) · manifest.ts · ui/ · demo/ (if D4 = per-module demo)
    attendance/
    academics/
    fees/
    examinations/
  app/
    (core)/…                # login, account, admin/settings, admin/permissions, admin/audit, dashboards (shells)
    (students)/admin/students/…, admin/promotions/…, student/certificates/…, verify/tc/…
    (attendance)/…  (academics)/…  (fees)/…  (examinations)/…
  modules.generated.ts      # GENERATED: static imports of the selected manifests only
convex/
  core/  model/(core)  auth.ts users.ts schools.ts … structure.ts
  students/  attendance/  academics/  fees/  examinations/     # each: schema.ts, contract.ts, public functions, model/
  schema.ts                 # imports ./modules.generated → composes Core + selected module tables
  modules.generated.ts      # GENERATED: selected module schema fragments, crons, providers
  crons.ts                  # built from Core + selected modules' cron contributions
distributions/
  products.json             # named products, e.g. "students-attendance": ["students","attendance"]
scripts/
  distribute.ts             # export + verify (see §8)
```

Route groups `(students)` etc. do not change URLs, so excluding a module is "do not copy `src/app/(students)`". Next.js then never discovers those routes.

### 4.2 Target dependency matrix (requires ⇒ always shipped together; optional ⇒ integrates through a contract when present)

| Module | Requires | Optional integrations (contract, not import) |
|---|---|---|
| Core | — | — |
| Students | Core | Fees (dues gate, ledger panel), Examinations (results panel, promotion standing), Attendance (attendance panel, TC working days), Academics (timetable panel) |
| Attendance | Core, Students | Academics (subject attendance / periods, future) |
| Academics | Core | Students (rosters for homework/timetable views) |
| Fees | Core, Students | — |
| Examinations | Core, Students, Academics (subjects, teacher assignments) | Attendance (report-card attendance) |

The graph is acyclic: Core ← Students ← {Attendance, Fees}; Core ← Academics ← Examinations ← Students. Optional integrations run **through Core-owned contracts and registries**, never imports, so they cannot create cycles. The build rejects any manifest whose `requires` closes a cycle (§9 D).

Valid products include `students`, `students+attendance`, `students+fees`, `academics`, `students+academics+examinations`, and all five. **Invalid:** `examinations` without `academics` and `students`; `attendance` without `students`; `fees` without `students`. Selections are never silently completed: the script reports the missing dependency and stops.

### 4.3 Public contracts

`src/contracts` and `convex/contracts` hold one dependency-free source shared by both sides:

- **Branded ids**: reuse Convex `Id<"students">`, `Id<"sections">` etc. as the contract (already branded by Convex). For values crossing UI/URL boundaries, add `parseId(table, value)` validators, so there are no bare `as Id<…>` casts in new code.
- **Module manifest** type (§4.4) and `ModuleKey` (the new key set).
- **Provider interfaces**, for example `StudentDuesProvider { outstanding(ctx, studentId, yearId): Promise<Money | null> }`, `StudentProfileSection`, `ReadScopeProvider`, `FileKindAuthorizer`, `DashboardPanel`. A module implements a provider in its own folder and registers it in its manifest. Consumers ask the registry and must handle "not installed".
- **Event types** (§4.5).

Rule enforced by lint/test: a module may import only `contracts`, `core`, and the `index.ts` / `contract.ts` of modules it **requires**. Deep imports into another module's folder fail the build check.

### 4.4 Module manifest

```ts
// src/modules/attendance/manifest.ts (frontend) + convex/attendance/manifest.ts (backend), same id/version
export const manifest = defineModule({
  id: "attendance", version: "1.0.0", entitlementKey: "attendance",
  requires: ["students"], optional: ["academics"],
  permissions: ["attendance:read:all", "attendance:read:assigned", "attendance:read:own", "attendance:mark:class_teacher", "attendance:edit:class_teacher"],
  routes: [{ group: "(attendance)", paths: ["/admin/attendance", "/teacher/attendance", "/student/attendance"] }],
  nav: [{ role: "admin", label: "Attendance", href: "/admin/attendance", icon: "attendance", anyOf: ["attendance:read:all"] }, …],
  backend: { dir: "convex/attendance", tables: ["attendanceSessions", "attendanceRecords"], crons: [], migrations: ["2026-11-attendance-001"] },
  events: { emits: ["attendance.absence_recorded@1"], listens: ["students.withdrawn@1"] },
  contributes: { dashboardPanels: ["teacher.registerToday", "admin.attendanceTrend"], studentProfileSections: ["attendance"] },
  tests: ["tests/modules/attendance/**"],
});
```

The manifest **describes** what the folder contains and is checked against it (the routes, tables and functions listed must exist and must be the only ones the module owns). It never hides code. Hiding is replaced by exclusion.

### 4.5 Cross-module events

Today's cross-module **side effects** are few. Writes are owner-only, and reads become contracts. The ones that matter, such as student withdrawn / transferred / promoted / passed out (Fees may stop raising future dues, and Attendance closes open registers), use:

- **Versioned, typed payloads** (`students.withdrawn@1 { schoolId, studentId, enrollmentId, effectiveDate }`).
- **Durable outbox**: the emitter inserts a `moduleEvents` row **in the same Convex mutation** as the business change. A scheduled internal dispatcher delivers it to each registered listener in its own mutation, records per-listener status, and retries with backoff. Failures go to a dead-letter status visible in the audit log. This is the transactional-outbox pattern; nothing relies on an in-memory bus.
- **Absent listeners**: the dispatcher iterates registered listeners. With none installed, the event is marked delivered. Emitters never import listeners.
- **Ownership**: the emitting module owns the event type and its versions; listeners own their handlers. A breaking change adds `@2` and keeps `@1` until all listeners move.
- **Synchronous reads stay synchronous** (providers), and only **side effects** are events.

### 4.6 Next.js integration

- `src/modules.generated.ts` is written by the export script (and checked in as the "all modules" variant for development). It statically imports only the selected manifests. Nav, route guards, dashboard panels and profile sections are built from it, then filtered by server-derived permissions **and** entitlements, exactly as today.
- No runtime-variable `import()` of module paths, which Next.js cannot tree-shake or verify. Exclusion is physical.
- Shared shells (dashboards, student portal, My Classes) render contributed panels. An excluded module contributes nothing, so there are no dead links.

### 4.7 Convex isolation strategy

**Chosen: one Convex project per distribution, modules as folders, composed schema, regenerated codegen.**

1. Each module's backend lives in `convex/<module>/`. Its tables are exported from `convex/<module>/schema.ts` as a plain object of `defineTable(...)`.
2. `convex/schema.ts` = `defineSchema({ ...coreTables, ...structureTables, ...selectedModuleTables })`, where the selection comes from the generated `convex/modules.generated.ts`.
3. The export script copies only Core + selected module folders, writes `modules.generated.ts`, then runs `npx convex codegen`. **This answers `_generated/api.d.ts`**: it is regenerated from the files physically present, so it contains only Core and the selected modules. Frontend code that referenced an excluded module's `api.fees.*` cannot exist in the export, because that code lives in the excluded module's folder. Any stray reference is a TypeScript error caught by the verification step.
4. Entitlement checks (`moduleQuery("fees")`) stay. A delivered module can still be switched off per school, and in our own multi-school SaaS deployment (all modules) entitlements remain the only gate.
5. **Data preservation on removal**: a distribution for a school that previously ran a module keeps that module's **table definitions** in a `retainedTables` fragment (schema only, no functions), so `convex deploy` never has to drop or invalidate existing documents and no business data is deleted. Removing data is a separate, explicit, audited operator action. *To verify on a scratch deployment before relying on it (needs your approval): Convex's behaviour when a populated table is absent from the schema. The retained-schema approach avoids depending on it either way.*

**Considered and not chosen now:**

- *Convex Components per module*: true table isolation, but component functions are not client-facing and cannot read the app's tables or auth directly. Every module function would need an app-level wrapper, every cross-module read becomes a component call, and auth/tenancy has to be passed in. That is high cost for no extra isolation once source is excluded. Revisit if modules must be sold as drop-in add-ons to a running deployment.
- *Separate deployments per module*: cross-module reads become HTTP calls, auth is split across deployments, and transactions are lost. Not justified.

### 4.8 Distribution boundary

`scripts/distribute.ts --product students-attendance --out ../dist/aster-students-attendance` (§8) produces a **fresh directory with no `.git`**. Delivery is that tarball, or a new private repository initialised from it. Module packages on a private registry are possible later, but would not remove the need for exclusion, so they are not needed for this phase.

## 6. Migration sequence (smallest safe steps; each ends green: tsc, vitest, build, E2E)

0. **Guards first, no moves**: add `scripts/module-ownership.ts` (the audit scan as a test) plus a test failing on any *new* forbidden cross-module import. Record current violations as a shrinking allow-list.
1. **Contracts + registries**: `contracts/` (manifest type, provider and event types, id parsing), the Core registries (nav, routes, panels, profile sections, file kinds, scope providers, crons), and the `moduleEvents` outbox + dispatcher. Nothing consumes them yet.
2. **Split mixed files**: `convex/academics.ts` → structure / students / assignments (B7); move student account creation out of Core (B3); file-kind authorisers (B4); read-scope providers (B2).
3. **Extract Fees** (cleanest: owner-only writes, one cron, one cycle with Students to break via B5/B6). This proves the export pipeline on a real module.
4. **Extract Examinations** (new entitlement key, D2), then **Academics** (subjects, assignments, timetable, homework).
5. **Extract Attendance**, then **Students**; Students last because everything integrates with it.
6. **Adapters → contributions**: dashboards, reports, student portal, teacher workspace / My Classes.
7. **Schema composition + generated registries**; `distribute.ts`; product matrix tests.
8. **Verify** a Students + Attendance export end-to-end (§9); document delivery.

Every step keeps today's behaviour and business rules. During steps 3–6, old API paths may stay as thin re-exports for one release, so nothing outside the moved module breaks mid-way.

## 8. Export script design (`scripts/distribute.ts`)

1. Read `distributions/products.json` and module manifests. Validate: known ids, no duplicates, every `requires` present (fail, never auto-add), no cycles.
2. Compute the closure: Core + selected modules. Build an **allow-list** of paths: Core folders, `contracts/`, each selected module's `src/modules/<m>`, `src/app/(<m>)`, `convex/<m>`, tests, and root config. Everything else is excluded by default (deny-by-default).
3. Copy into a fresh directory (no `.git`, no `.next`, no `node_modules`). Write `src/modules.generated.ts`, `convex/modules.generated.ts` (and `retainedTables` if requested). Prune `package.json` dependencies to those declared by Core + the selected manifests.
4. **Verify**:
   - forbidden-path scan: no excluded module folder, route group or table name;
   - forbidden-reference scan: no `@/modules/<excluded>`, `api.<excluded>`, excluded table names in source;
   - `npm ci`, `npx convex codegen`, `tsc --noEmit` (app + convex), `vitest` (Core + selected module tests), `next build`.
5. Emit `DISTRIBUTION-REPORT.md` + `distribution.json`: product, modules and versions, file list with hashes, packages, routes, Convex functions (from the generated API) and tables. Any failed check exits non-zero and leaves no "ready" marker.
